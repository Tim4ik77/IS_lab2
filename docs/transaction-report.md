# Исследование изоляции транзакций

Результаты сохранённого исследования до очистки проекта. Дата: 15.11.2026. Среда: Windows, Java 17.0.12, Spring Boot 3.5.6, EclipseLink 4.0.8, локальная PostgreSQL 18, JMeter 5.6.3. Использована отдельная тестовая БД; данные ЛР1 не затрагивались.

## Гипотеза и сравнение

Новое бизнес-правило проверяет отсутствие события/площадки с таким же названием после Java-нормализации. В БД нет соответствующего UNIQUE-ограничения. Обычная последовательность «проверить отсутствие, затем вставить» допускает гонку: два пользователя одновременно видят отсутствие объекта.

Отдельный JDBC-эксперимент, выполненный до очистки проекта, открывал два независимых JDBC-соединения. Оба выполняют тот же запрос названий событий, что и бизнес-проверка, затем барьер гарантирует, что оба прочитали данные до вставок. Оба вставляют одинаковое название и пытаются завершить транзакции. Для каждого уровня используется новый UUID, после измерения удаляются только записи этого эксперимента.

| Изоляция | Транзакция 1 | Транзакция 2 | Строк с одинаковым именем |
|---|---|---|---|
| READ COMMITTED | COMMIT | COMMIT | 2 |
| REPEATABLE READ | COMMIT | COMMIT | 2 |
| SERIALIZABLE | COMMIT | 40001, ROLLBACK | 1 |

Это контролируемый эксперимент с SQL-последовательностью бизнес-правила, а не заявление о запуске старой версии приложения. Итоговое приложение проверено отдельно через HTTP/JMeter.

PostgreSQL `REPEATABLE READ` даёт стабильный снимок, но не предотвращает данную аномалию сериализации. `SELECT FOR UPDATE` тоже недостаточен: отсутствующую строку заблокировать нельзя. `SERIALIZABLE` отслеживает зависимости чтений/записей и отменяет несовместимые конкурентные транзакции. Основание: [документация PostgreSQL об изоляции](https://www.postgresql.org/docs/current/transaction-iso.html).

## Принятое решение

Все изменяющие операции предметной области используют `SERIALIZABLE`: создание, редактирование, удаление/перенос ссылок, импорт и специальные операции. Это консервативный единый режим для связанного графа объектов: чтения ссылок, проверки названий и записи относятся к одной сериализуемой транзакции. Особенно необходим режим для Event/Venue и импорта, где проверка уникальности читает множество строк. Чтение списков/деталей и независимое создание/завершение ошибочной записи журнала используют `READ COMMITTED`.

Для EclipseLink настроен `EclipseLinkJpaDialect` с `lazyDatabaseTransaction=false`; уровни указаны явно для сервисных транзакций. Общий кэш EclipseLink выключен. Успешный журнал импорта не открывает отдельную транзакцию, а присоединяется к импорту. Настройки соответствуют [документации Spring EclipseLinkJpaDialect](https://docs.spring.io/spring-framework/docs/6.2.16/javadoc-api/org/springframework/orm/jpa/vendor/EclipseLinkJpaDialect.html).

При конфликте сервер возвращает 409 и не скрывает откат. UI предлагает повторить действие через текст ошибки; бесконтрольных автоматических повторов записи нет. `@Version` и `If-Match` отдельно предотвращают перезапись билета из устаревшей формы, даже если запросы пришли последовательно. SQL-продажа и JPQL-перенос ссылок также увеличивают version.

Нормализация названий реализована в Java, поэтому не зависит от locale/collation PostgreSQL и работает для кириллицы. Проверка читает имена всех объектов нужного справочника. Цена простоты — полное сканирование и более широкие SSI-зависимости. На больших справочниках это потребует оптимизации и повторного нагрузочного исследования; текущий режим ориентирован на учебную ИС.

## JMeter: проверка приложения через HTTP

План: [`../tests/jmeter/lab2.jmx`](../tests/jmeter/lab2.jmx); код: `scenario.groovy`. Четыре одновременно работающих пользователя: admin, admin2, user, user2. Пять раундов; перед каждой гонкой все потоки ждут общего барьера. Setup создаёт отдельные билеты для update/update, delete/delete и update/delete. После раундов выполняется независимая проверка конечного состояния.

| Сценарий | Результат за 5 раундов |
|---|---|
| Одинаковое имя события | 5 × 201; 15 × 409; по одному объекту на имя |
| Одинаковое имя площадки | 5 × 201; 15 × 409; по одному объекту на имя |
| Изменение одного билета с общей version | 5 × 200; 15 × 409; версия выросла ровно на 1 |
| Удаление одного билета | 5 × 204; 13 × 409; 2 × 404; билет отсутствует |
| Изменение против удаления | 5 × 204; 10 × 409; 5 × 404; в данном запуске победили удаления |
| CRUD собственных билетов | 20 полных последовательностей create → update → delete |
| Успешный импорт | 20 × 201; SUCCESS, addedCount=1, правильный владелец |
| Ошибка во второй записи импорта | 20 × 400; FAILED, addedCount=null; нет билета и новых справочников первой записи |
| Импорт против создания того же события с другими полями | 5 × 201; 15 × 409; по одному событию |
| История и роли | 20 проверок; пользователь видит только себя, администратор видит других |

**Итог: 202 JMeter samples, 0 ошибок assertions**, 22 секунды, среднее время sample 332 мс. Sample здесь — этап сценария, который может включать несколько HTTP-запросов и ожидание барьера; это не отдельный HTTP-request и не измерение предельной производительности.

В независимых операциях зафиксировано **32 дополнительных ответа 409**, после которых клиент сценария ограниченно повторил полностью отменённую операцию. Они учитывались отдельно и не считались успешными первыми попытками. Для гонок одного уникального имени или общей version повторы запрещены. Это показывает практическую цену выбранного консервативного уровня изоляции.

Ограничения исследования: один экземпляр приложения, четыре пользователя, пять раундов, localhost. Это проверка требуемых конкурентных сценариев, а не доказательство всех возможных расписаний и не benchmark производственной нагрузки. Гарантия уникальности требует, чтобы изменения выполнялись через новую бизнес-логику; прямой SQL и старая версия ЛР1 могут её обойти, поскольку по условию UNIQUE в БД запрещён.
